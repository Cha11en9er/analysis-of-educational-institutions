# Подбор школ по приоритетам («Что вам важно в школе?»)

Документ фиксирует продуктовую логику и **как именно** бэкенд считает балл совпадения. Данные по школам и отзывам **неполные**: часть школ не попала в парсинг Госуслуг, а нейро-анализ отзывов есть только для ограниченного набора `school_id`. Для таких школ по отдельным осям используется **нейтральное значение 0.5** после нормализации (см. ниже), чтобы они не выпадали из выдачи без причины, но и не получали необоснованного преимущества.

## Источники данных

| Ось | Источник | Файл / место |
|-----|----------|----------------|
| Олимпиады, ЕГЭ, ВУЗ, паспорт здания, инфраструктура (списки) | Парсинг карточек Госуслуг | `parsing/school_gosuslugi/sg_data/sg_data_output/sd_2_stage_gosuslugi_infrastucture_output.json` |
| Координаты для карты в продукте | БД `sa.school` (эндпоинт `/api/schools/map`) | Поле `location`; JSON `school_data/sd_2_stage_gosuslugi/sd_2_stage_gosuslugi.json` — эталон при обновлении БД |
| Буллинг, учителя, администрация, ремонт, инфраструктура (субъективно) в **подборе по приоритетам** | Промежуточные файлы анализа | `review_data/rd_2_stage_analys/rd_separately_analyzed/school_reviews_separately_{id}_analyz.json` |
| **Графики на сайте, API `/api/schools/{id}/reviews/topics`, таблица `sa.review`** | Финальные отзывы (текст + дата + topics) | `review_data/rd_3_stage/rd_3_stage_data/school_review_separately_{id}_final.json` → загрузка скриптом `db/db_src/db_insert/db_insert_data_review.py` |
| Малиновая точка на карте («есть отзывы как в графиках») | Наличие `*_final.json` в rd_3_stage | То же множество `school_id`, что попадает в БД после импорта |

Идентификатор школы везде: **`school_id` = `id` в JSON**.

**Разделение:** `rd_2_stage_analys` — только «разобранные» темы (удобно для офлайн-скоринга в `preference_scoring.py`). **`rd_3_stage`** — объединённый результат (тело отзыва, дата, topics), именно он импортируется в БД и строит графики по датам.

## Шесть категорий в форме

1. **Олимпиадная активность** — численные строки из блока `Olympiads` (призёры/победители, уровень этапа).
2. **Отношение к ребёнку / буллинг** — тема `буллинг` в отзывах (`pos` / `neg` / `neutral`).
3. **Учителя и администрация** — темы `учителя`, `администрация`.
4. **Ремонт и характеристики школы** — смесь отзывов (`ремонт`, `инфраструктура`) и паспорта здания из JSON.
5. **Обучение и ЕГЭ** — поля `EGE` (средний балл) и `VUZ` (доля поступивших в вузы), парсятся из текстовых строк.
6. **Близость расположения** — расстояние от точки пользователя (`user_lat`, `user_lon`) до координат школы из БД (формула гаверсинуса).

Пользователь может **закрыть попап** и пользоваться картой без подбора; выбранные приоритеты не обязательны.

## Общая формула итогового балла

Пусть пользователь отметил множество осей \(S\). Для каждой школы по каждой оси \(i \in S\) считается значение \(m_i \in [0, 1]\). Итог:

\[
\text{score} = \frac{1}{|S|} \sum_{i \in S} m_i
\]

В API возвращается **`preference_score`** = `round(score * 100, 1)` и **`preference_breakdown`** — вклад каждой выбранной оси в процентах (те же \(m_i \cdot 100\)).

**Веса между осями равномерные**: каждая отмеченная категория имеет одинаковый вес \(1/|S|\). Так проще объяснить пользователю и не требует ручной калибровки под выборку из ~15 школ с отзывами.

Если нужны неравные веса в будущем — достаточно заменить среднее на взвешенную сумму с нормализацией суммы весов к 1.

## Как считается каждая ось (детали реализации)

### 1. Олимпиады

- Из каждой строки `Olympiads` извлекается ведущее целое число (количество человек).
- На строку накладываются множители **уровня этапа** (по подстрокам в нижнем регистре):
  - заключительный этап — ×4  
  - региональный — ×2.5  
  - муниципальный — ×2  
  - школьный — ×1  
  - общее упоминание всероссийской олимпиады без уточнения этапа — ×2  
- Если в строке есть «победител» — дополнительный коэффициент ×1.3 (призёры ×1).
- По школе суммируется вклад строк, затем берётся `log1p(сумма)` для сглаживания выбросов.
- По всем школам, у которых есть непустой `Olympiads`, значения **нормализуются min–max** в \([0, 1]\).
- Школа без данных по олимпиадам получает **0.5** на этой оси.

### 2. Буллинг

- По всем отзывам в `school_reviews_separately_{id}_analyz.json` берётся тема `буллинг`: `pos` → 1, `neg` → 0, `neutral` → 0.5.
- Метрика — **среднее** по всем вхождениям темы в отзывах этой школы.
- Затем **min–max по школам**, у которых есть хотя бы один отзыв с этой темой. Школа без таких отзывов на оси буллинга: **0.5**.

Интерпретация: высокий балл = чаще позитивные упоминания климата/отсутствия обид; низкий = чаще негатив.

### 3. Учителя и администрация

- Аналогично буллингу, но темы **`учителя`** и **`администрация`** объединяются: в среднее попадают все вхождения обеих тем.
- Нормализация min–max по школам с данными; иначе **0.5**.

### 4. Ремонт и характеристики

Две части, затем смешивание:

**A. Отзывы (≈45% итога по оси):** среднее сентимента по темам `ремонт` и `инфраструктура` (если обе есть — среднее двух средних по темам внутри школы реализовано как среднее по всем вхождениям обеих тем). Min–max по школам с данными.

**B. Паспорт здания (≈55%):** нормализованный составной индикатор из полей JSON:

- тип здания: содержит «новыми корпусами» — высокий вклад, иначе базовый;
- `area_sqm` — через `log1p`, масштабирование к разумному верху;
- `floors` — до потолка (например норма на 12 этажей);
- `reconstruction_year` — новее ремонт выше (линейная шкала от условного 1980 к текущему году);
- `infrastucture` (список объектов) — доля от условного максимума количества пунктов.

Части B нормализуются min–max по школам с JSON-полями. Итог по оси: **`0.55 * B_норм + 0.45 * A_норм`**, с подстановкой **0.5** за отсутствующую половину.

### 5. ЕГЭ и ВУЗы

- Из строки `EGE` извлекается средний балл (поддерживаются форматы с запятой/точкой).
- Из `VUZ` — процент поступивших в вузы.
- Каждое измерение нормируется min–max отдельно по выборке; итог оси: **среднее двух нормированных**, если оба есть; если одно — оно и есть метрика; если ни одного — **0.5**.

### 6. Близость

- Расстояние \(d\) в км (гаверсинус) между (`user_lat`, `user_lon`) и координатами школы.
- \(m_{\text{loc}} = 1 / (1 + d/3)\) — тем ближе, тем ближе к 1.
- Если пользователь включил эту ось, **обязательны** `user_lat` и `user_lon` (иначе 400 от API).

## Поведение API

- Эндпоинт: `GET /api/schools/map` с булевыми query-параметрами `pref_olympiads`, `pref_bullying`, `pref_staff`, `pref_building`, `pref_exam`, `pref_location` и опционально `user_lat`, `user_lon`.
- Если **ни один** приоритет не передан — список как раньше, порядок по `school_id`, поля `preference_score` / `preference_breakdown` = `null`.
- Если хотя бы один приоритет **true** — школы **сортируются по убыванию `preference_score`**, в ответ добавляются баллы.

Реализация: модуль `api/preference_scoring.py`.

## Ограничения и развитие

- При малом числе школ с отзывами min–max по «буллингу» и «учителям» шумный; по мере роста выборки метрики стабилизируются.
- Можно добавить **явный штраф за отсутствие данных** по выбранной оси вместо 0.5, если нужно «только школы с доказательствами».
- Координаты из JSON школ можно периодически **синхронизировать в PostGIS**, чтобы карта и подбор всегда совпадали с одним источником.
