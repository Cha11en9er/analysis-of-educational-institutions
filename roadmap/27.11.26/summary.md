# 27.11.26 — подготовка к наплыву пользователей (оптимизация и отказоустойчивость)

Задача от владельца: сайт должен выдержать резкий наплыв, ничего не должно падать.
Рассматривался брокер сообщений (NATS): для этого сайта он не нужен — нагрузка
read-only (карта + справка), фоновых задач нет. Правильный набор: пул соединений
БД, кэш ответов с отдачей устаревших данных при сбое, несколько воркеров,
сжатие и мягкий лимит в nginx. Всё реализовано и проверено на проде.

## Что сделано

### 1. Пул соединений PostgreSQL (api/db_pool.py)
Раньше каждый запрос открывал своё соединение psycopg2 — при всплеске это
упирается в лимит соединений БД и добавляет задержку. Теперь ThreadedConnectionPool
(до 10 соединений на воркер, 40 суммарно при 4 воркерах), close() возвращает
соединение в пул (обработчики менять не пришлось), «пинг» при выдаче переживает
перезапуск БД.

### 2. Кэш ответов с отказоустойчивостью (api/cache.py + middleware)
GET-ответы кэшируются в памяти: карта 15 с, учреждения 15 с, карточка школы и
темы отзывов 60 с, зоны прикрепления 120 с, конфиг 300 с. Кэшируется тело только
HTTP 200 до 3 МБ (до 1200 записей). При падении БД обработчик возвращает ошибку,
а middleware отдаёт последнюю известную копию с пометкой X-Cache: stale —
проверено на проде: остановил postgres, 8 из 8 запросов отдали данные (6 stale,
1 hit, 1 miss). TTL короткие, поэтому данные на сайте остаются свежими.

### 3. Несколько воркеров uvicorn
systemd-юнит: --workers 4. Каждый воркер со своим пулом и кэшем; суммарно до
40 соединений БД (лимит postgres по умолчанию 100).

### 4. nginx
- gzip для JSON и статики (ответ карты ~70 КБ -> ~12 КБ);
- кэш браузера на неделю для /images/ (фото заведений);
- мягкий лимит 30 req/s с burst 60 на /api/ (от скрейперов и DDoS, не для
  честных пользователей; NAT-клиенты проходят);
- таймауты к апстриму 3/20 с; /healthz проксируется для мониторинга;
- живой конфиг синхронизирован в репозиторий (deploy/nginx-uchgrad.ru.conf).

### 5. /healthz
Лёгкая проверка без БД (для nginx и внешнего мониторинга).

### 6. GZip middleware в FastAPI
Сжимает и свежие, и кэшированные ответы.

## Проверки на проде
- 8 подряд GET /api/schools/map: 3 холодных ~75 мс, затем из кэша ~2 мс;
- 100 запросов с конкурентностью 20: 100 ответов 200;
- останов postgres: все запросы отдали данные из кэша (X-Cache: stale/hit);
- gzip на ответе подтверждён (content-encoding: gzip);
- nginx -t успешен, конфиг в репозитории.

## Что можно сделать дальше (не срочно)
- Вынести кэш в общий слой (Redis), когда появится второй сервер или если
  анкет-список вырастет; сейчас 4 независимых кэша воркеров дают 4x выигрыш
  и уже снимают нагрузку.
- Мониторинг внешним таймером (UptimeRobot на /healthz) — рекомендую настроить.
- Postgres: разогреть pg_prewarm не требуется; при росте данных рассмотреть
  материализованное представление карты.

## Вечер: логика первичного фильтра (по заявке владельца)

Владелец: при первом входе модалка «что вам интересно» при неудачном выборе давала
0 школ; нужна явная кнопка «просто показать школы». Связь QR-кода с сайтом не менять
(QR из презентации ведёт на https://uchgrad.ru/ — главную, маршрут не тронут).

- Причина «0 школ» найдена: галочка «Близость расположения» без полученных
  координат уходила в API и падала 400, список обнулялся. Теперь «Применить»
  в этом состоянии блокируется с подсказкой (нажать «Моё местоположение» или
  снять галочку) — проверено: список из 128 школ не трогается.
- Новая кнопка «Мне не интересны фильтры, просто показать школы» в модалке:
  снимает галочки и фильтры, закрывает окно, остаётся обычный список (128 школ,
  без чипов). Крестик и клик по фону работали так же и раньше.
- Выход из «0 школ» в один клик: в пустом состоянии списка кнопка
  «Сбросить фильтры и поиск» — снимает фильтры, поиск и подбор сразу.
- QR-код презентации декодирован: https://uchgrad.ru/ (главная). Маршруты
  / и /school/{id} не менялись — связь кр-кода с сайтом сохранена.
